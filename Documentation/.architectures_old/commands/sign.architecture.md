# Tayku Web Client Sign Command Architecture

The "`sign`" command is one of the commands available in the Tayku Web Client. It provides the user-facing interface for signing Tayku packages and projects.

The command determines the signing target from the command arguments and invokes the Verifier module to perform the signing operation.

The "`sign`" command does not implement the cryptographic signing mechanism itself.

The cryptographic signing mechanism, key derivation, Ed25519 implementation, and signature verification are defined by the Verifier architecture.

The command supports two signing types:

```sh
npx tayku-web sign --package
npx tayku-web sign --project
```

The command must be executed from the location containing the corresponding Tayku configuration file.

# 1. In-Scope
* **In-Scope**  
	* Determine the signing type from the command arguments.
	* Determine whether a package or project is being signed.
	* Validate the current filesystem location.
	* Locate the Tayku package or project configuration.
	* Locate the developer user's secret seed.
	* Determine the appropriate secret seed when multiple seeds are available.
	* Invoke the Verifier module with the signing target and secret seed.

	* Requiring a name for a developer user.
	* Requiring a developer user number.
	* Modifying the Verifier cryptographic contract.
	* Parsing command-line arguments.
	* Rendering command output.

# 2. Architecture

This section examines the architecture and responsibilities of the "`sign`" command.

## 2.1 Logic

The "`sign`" command acts as an abstraction layer between the CLI layer, the local Tayku package or project, and the Verifier module.

The command determines the signing target from the supplied command arguments.

The supported signing types are:

* **Package**
	* Signs the package represented by the local "`tayku-package.json`".

* **Project**
	* Signs the project represented by the local "`tayku-project.json`".

The signing operation requires a developer user's secret seed.

The developer user's secret seed is generated by:

```sh
npx tayku-web init --developer-user
```

The developer user seed is 32 bytes in length.

The Verifier module deterministically derives the Ed25519 key material from this seed.

The derivation of the public and private keys is defined by the Verifier architecture.

The "`sign`" command does not perform key derivation itself.

The "`sign`" command locates the available developer user secret seed and provides it to the Verifier module.

If no developer user secret seed is available, the signing operation cannot be performed.

If more than one developer user secret seed is available, the command requires the user to select the seed to be used.

The developer user system does not require an email address, name, developer number, or another user-defined identity condition for selection.

The "`sign`" command does not determine the cryptographic identity represented by a seed.

The selected seed is passed to the Verifier module, which performs the signing operation according to its cryptographic contract.

· · ·

## 2.2 Definitions

* **Signing Target:** The local Tayku package or project selected for signing.

* **Package Signing:** The operation of signing the package represented by "`tayku-package.json`".

* **Project Signing:** The operation of signing the project represented by "`tayku-project.json`".

* **Developer User:** A Tayku developer identity created through "`npx tayku-web init --developer-user`".

* **Secret Seed:** The 32-byte seed generated for a developer user and used as the deterministic input for Ed25519 key derivation.

* **Ed25519:** The public-key signature algorithm used by the Verifier module.

* **Verifier Module:** The module responsible for key derivation, signing, and signature verification according to the Verifier architecture.

* **Seed Selection:** The process of selecting one developer user secret seed when multiple seeds are available.

# 3. Interface

## 3.1 Inputs

The "`sign`" command accepts a signing type.

### Package

```sh
npx tayku-web sign --package
```

The command signs the package represented by the local "`tayku-package.json`".

### Project

```sh
npx tayku-web sign --project
```

The command signs the project represented by the local "`tayku-project.json`".

The command does not currently accept a signing target path as an argument.

The signing target is determined from the current filesystem location.

· · ·

## 3.2 Outputs

The "`sign`" command returns a "`TAYKU-STATUS-CODE`".

When the signing operation is completed successfully, the resulting signature is applied according to the Verifier and package or project contracts.

When the signing operation cannot be performed, the corresponding failure status code is returned.

The "`sign`" command does not define the cryptographic representation of the generated signature.

· · ·

## 3.3 Dependencies

The "`sign`" command depends on the following components:

* **CLI Parser**  
	* Parses the command-line arguments before they are passed to the "`sign`" command.

* **Verifier Module**  
	* Provides Ed25519 key derivation.
	* Provides package and project signing functionality.
	* Defines the cryptographic signing contract.

* **Filesystem**
	* Provides access to the local Tayku package or project configuration.
	* Provides access to developer user secret seed data.
	* `fs`

* **Runtime Environment of JS**
	* `nodejs`

The command does not implement the cryptographic functionality provided by the Verifier module.

· · ·

## 3.4 Source Contract

The "`sign`" command receives the signing type from the CLI layer.

A conceptual interface is defined as follows:

```js
/**
 * Signs a Tayku package or project.
 *
 * Resolves the local signing target, locates the developer
 * user secret seed, and invokes the Verifier module.
 *
 * @param {string} type The signing type.
 *
 * @returns {number} TAYKU_STATUS_CODE
 */
function sign(type) {...}
```

The "`type`" parameter determines whether a package or project is signed.

The signing target is resolved from the current filesystem location.

The developer user secret seed is resolved by the "`sign`" command and passed to the Verifier module.

The "`sign`" command does not perform Ed25519 key derivation or signature generation itself.

The return value communicates operation status to the CLI layer.

## 3.6 Command Behavior

**What happens when "`--package`" is specified?**

The command validates the current filesystem location.

The command searches for the local "`tayku-package.json`" required to identify the package.

The developer user secret seed is resolved.

The Verifier module is invoked with the package and selected secret seed.

The Verifier module derives the required Ed25519 key material deterministically from the seed and performs the signing operation according to its contract.

The resulting "`TAYKU-STATUS-CODE`" is returned to the CLI layer.

· · ·

**What happens when "`--project`" is specified?**

The command validates the current filesystem location.

The command searches for the local "`tayku-project.json`" required to identify the project.

The developer user secret seed is resolved.

The Verifier module is invoked with the project and selected secret seed.

The Verifier module derives the required Ed25519 key material deterministically from the seed and performs the signing operation according to its contract.

The resulting "`TAYKU-STATUS-CODE`" is returned to the CLI layer.

· · ·

**What happens when the command is executed from an invalid location?**

If the required "`tayku-package.json`" or "`tayku-project.json`" cannot be resolved from the current location, the signing operation is not performed.

An appropriate "`INVALID LOCATION`" status code is returned.

· · ·

**What happens when no developer user secret seed exists?**

If no developer user secret seed can be found, the signing operation is not performed.

The command does not generate a new seed automatically.

An appropriate "`SECRET SEED NOT FOUND`" status code is returned.

· · ·

**What happens when multiple developer user secret seeds exist?**

If multiple developer user secret seeds are available, the command does not select one automatically.

The user is presented with the available seeds and is required to select one.

The command does not require an email address, name, number, or another developer identity attribute for this selection.

After the user selects a seed, the selected seed is passed to the Verifier module.

· · ·

**What happens when the user does not select a seed?**

If multiple seeds are available and the user does not provide a valid selection, the signing operation is not performed.

An appropriate "`INVALID ARGUMENT`" status code is returned.

· · ·

**What happens when the Verifier module fails?**

If the Verifier module reports a failure during key derivation or signing, the "`sign`" command propagates the resulting "`TAYKU-STATUS-CODE`" to the CLI layer.

The command does not reproduce or replace the functionality of the Verifier module.

# 4. Error Handling

The "`sign`" command may return errors generated by the CLI argument layer, local target resolution, developer user seed resolution, or the Verifier module.

* **Invalid Arguments**  
	* "`INVALID ARGUMENT`": The provided signing type or seed selection is invalid.

	* **Solution**: Use one of the supported forms:

```sh
npx tayku-web sign --package
npx tayku-web sign --project
```

* **Invalid Location**  
	* "`INVALID LOCATION`": The command was executed from a location that does not contain the required Tayku package or project configuration.

	* **Solution**: Execute the command from the location containing the appropriate "`tayku-package.json`" or "`tayku-project.json`".

* **Secret Seed Not Found**  
	* "`SECRET SEED NOT FOUND`": No developer user secret seed is available for signing.

	* **Solution**: Create a developer user with:

```sh
npx tayku-web init --developer-user
```

* **Multiple Secret Seeds**  
	* "`MULTIPLE SECRET SEEDS`": Multiple developer user secret seeds are available and a seed selection is required.

	* **Solution**: Select one of the available secret seeds presented by the command.

* **Permission Error**  
	* "`PERMISSION DENIED`": The required package, project, or developer user seed data cannot be accessed because of insufficient permissions.

	* **Solution**: Check the permissions of the relevant files and directories.

* **Filesystem Error**  
	* "`IO ERROR`": An unexpected input/output error occurred while resolving the signing target or developer user seed.

	* **Solution**: Check the filesystem and retry the operation.

* **Signing Error**  
	* "`SIGN ERROR`": The Verifier module could not complete the signing operation.

	* **Solution**: Check the Verifier module status and retry the operation.

Errors generated by the Verifier module are propagated to the CLI layer through the command's "`TAYKU-STATUS-CODE`".

# 6. Security

* **Secret Seed Protection**
	* The developer user secret seed must be treated as sensitive key material.
	* The secret seed must not be exposed through command output.
	* The secret seed must not be included in the generated signature.
	* The "`sign`" command must pass the seed only to the responsible Verifier interface.

* **Deterministic Key Derivation**
	* The "`sign`" command must not implement an alternative key derivation mechanism.
	* Key derivation must be performed according to the Verifier architecture.
	* The 32-byte developer user seed is the deterministic input defined by the Verifier architecture.

* **Local Target Security**
	* The signing target must be resolved from the expected Tayku configuration file.
	* User-provided arguments must not allow the command to sign an unintended filesystem resource.
	* The command must not sign a package or project when the required local configuration cannot be resolved.

* **Seed Selection**
	* When multiple secret seeds exist, the command must require explicit user selection.
	* The command must not silently select a seed based on an email address, name, number, or another undeclared identity attribute.

* **Responsibility Isolation**
	* The "`sign`" command is responsible for target resolution, seed resolution, and orchestration.
	* Cryptographic operations remain the responsibility of the Verifier module.

* **Thread Safety**
	* The Tayku Web Client "`sign`" command operates synchronously in this version.
	* The command does not perform concurrent signing operations.
