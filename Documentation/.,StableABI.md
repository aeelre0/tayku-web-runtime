# Tayku Web Stable ABI Architecture

The Tayku Web Client provides a stable user-facing command interface.

The commands provided to users are considered a stable interface of the Tayku Web Client.

Once a command and its behavior have been defined and included in the project, the command must not change its user-visible behavior in a way that breaks existing usage.

New functionality may be added to existing commands or new commands may be introduced.

A command may also be marked as deprecated in the future.

Deprecation does not mean that the command may arbitrarily change its behavior.

The existing command interface and its established behavior must remain compatible with existing users.

The stable interface applies to the user-facing command layer only.

Tayku Web does not provide a stable inner ABI or API for its internal modules, functions, structures, variables, or implementation details.

The internal implementation may be rewritten, replaced, or migrated to another programming language without requiring the user-facing command interface to change.

Although the Tayku Web Client does not guarantee the stability of its inner ABI or API, the project provides documentation describing the current internal architecture.

This documentation is intended to allow developers to understand how the current implementation works.

Changes to the internal implementation must be documented.

When an internal component changes, the architecture documentation must describe the previous implementation and the new implementation.

The documentation therefore acts as a historical record of the internal architecture without making the internal architecture a stable contract.

The Node.js implementation currently uses "`npx`" as part of the command invocation.

For example:

```sh
npx tayku-web search --project foo
```

A future implementation written in C may not require "`npx`":

```sh
tayku-web search --project foo
```

The "`npx`" prefix is therefore considered an implementation-specific invocation detail and not part of the stable command semantics.

Tayku Web releases are maintained through periodic mainline updates.

The mainline project is updated approximately once every three months.

Developer contributions accepted into the mainline repository are incorporated into the next scheduled mainline update rather than necessarily being released immediately.

Users are free to select and use the Tayku Web version they require.

The Tayku Web Client does not require users to automatically upgrade to the newest version.

The client may inform the user when a newer version is available, but upgrading remains the responsibility of the user.

# 1. In-Scope
* **In-Scope**
	* Define the stability requirements of the Tayku Web user-facing command interface.
	* Preserve established command names.
	* Preserve established command behavior.
	* Preserve the meaning of existing command arguments and options.
	* Allow new commands to be introduced.
	* Allow new functionality to be added without breaking existing command behavior.
	* Allow commands to be deprecated while preserving their established behavior.
	* Allow the internal implementation to change independently from the user-facing interface.
	* Allow the implementation language to change without requiring a change to command semantics.
	* Allow invocation details such as "`npx`" to differ between implementations.
	* Provide current documentation describing the internal architecture.
	* Preserve historical documentation of internal implementation changes.
	* Document previous and new implementations when internal components change.
	* Maintain periodic mainline releases.
	* Allow developers to contribute changes to the mainline repository for inclusion in a scheduled update.
	* Allow users to select the Tayku Web version they want to use.
	* Inform users when a newer version is available without forcing an automatic upgrade.
* **Out-of-Scope**
	* Providing a stable inner ABI.
	* Providing a stable inner API.
	* Guaranteeing the lifetime of internal functions.
	* Guaranteeing the lifetime of internal structures.
	* Guaranteeing the lifetime of internal variables.
	* Guaranteeing the lifetime of internal modules.
	* Guaranteeing the lifetime of internal data structures.
	* Guaranteeing that the implementation remains in JavaScript.
	* Guaranteeing compatibility with programs that depend on undocumented internal behavior.
	* Automatically upgrading user installations.
	* Providing immediate mainline releases for every accepted developer patch.

# 2. Architecture

This section examines the separation between the stable user-facing interface and the internal implementation of the Tayku Web Client.

## 2.1 Stable User Interface

The user-facing command interface is the stable interface of the Tayku Web Client.

Once a command has been accepted into the project, its established behavior becomes part of the stable interface.

For example, if the "`search`" command is defined to search for Tayku resources, a future implementation must continue to provide that behavior through the established command interface.

The implementation behind the command may change.

The command may internally use JavaScript, C, Go, or another implementation language in the future.

The user-facing semantics must remain compatible.

· · ·
## 2.2 Command Stability

Existing commands must not be changed in a way that breaks established user usage.

The following properties of an established command are considered part of its stable interface:

* Command name.
* Established arguments.
* Established options.
* Established option meanings.
* Established command behavior.
* Established user-visible results.
* Established error semantics where they form part of the command interface.

New options and functionality may be introduced when they do not invalidate existing usage.

A deprecated command may remain available for compatibility even when a newer interface is preferred.

· · ·
## 2.3 Implementation Independence

The stable command interface must not depend on the internal implementation language.

The current Node.js implementation may use JavaScript modules such as:

```js
Cli.js
Commands.js
Registry.js
Verifier.js
Installer.js
Init.js
```

These modules are implementation details.

They may be rewritten, reorganized, replaced, or removed without violating the stable interface.

For example, the internal implementation may migrate from JavaScript to C:

```text
User
 |
 v
Tayku Web CLI
 |
 v
C implementation
```

while preserving the same command semantics.

· · ·
## 2.4 Invocation Independence

The exact executable invocation is not necessarily part of the stable command semantics.

The current Node.js implementation may require "`npx`":

```sh
npx tayku-web verify --project foo
```

A future native implementation may use:

```sh
tayku-web verify --project foo
```

The difference between these invocations does not constitute a change in the command's behavior.

The stable interface concerns the command and its semantics rather than the runtime mechanism used to launch it.

· · ·
## 2.5 Inner ABI and API

Tayku Web does not guarantee a stable inner ABI or API.

Internal functions, structures, variables, modules, classes, interfaces, and other implementation details may change at any time.

An external program must not assume that an internal function will continue to exist merely because it exists in the current implementation.

For example, a program must not depend on an internal function such as:

```js
function verifyProject(project) {
	/* ... */
}
```

and assume that Tayku Web will preserve this function indefinitely.

The function may be renamed, removed, rewritten, moved to another module, or implemented in another language.

· · ·
## 2.6 Architecture Documentation

Although internal interfaces are not stable contracts, the current implementation must be documented.

Each architecture document describes how the corresponding component currently works.

When an internal implementation changes, the relevant architecture document must record the change.

For example:

```text
Version 1
	Function A performs verification using implementation X.

Version 2
	Function A was removed.
	Function B performs verification using implementation Y.

Version 3
	Function B was replaced.
	Function C performs verification using implementation Z.
```

The documentation must explain the transition between implementations.

Historical descriptions must not be removed merely because the implementation is no longer current.

This allows developers to inspect the evolution of an internal component across versions.

For example, if an internal function has changed six times during the 6.x.x release series, the architecture documentation may contain the historical descriptions of all six implementations.

The existence of this documentation does not make any of those internal implementations stable.

· · ·
## 2.7 Mainline Release Cycle

Tayku Web maintains a periodic mainline release cycle.

A mainline update is expected approximately once every three months.

Developer patches accepted into the mainline repository are accumulated for the next scheduled mainline update.

An accepted patch does not necessarily become available to users on the same day that it is submitted or accepted.

The mainline update therefore acts as the periodic integration point for accepted changes.

· · ·
## 2.8 Version Selection

Users may select the Tayku Web version they want to use.

A newer version does not automatically replace an older version solely because it exists.

Users may continue using an older version when they choose to do so.

The project may inform the user that a newer version is available.

The decision to upgrade remains with the user.

# 3. Interface

## 3.1 Inputs

The stable interface consists of the user-facing Tayku Web commands and their established arguments and options.

The exact syntax of each command is defined by its corresponding command architecture.

Internal function signatures are not considered stable inputs.

· · ·
## 3.2 Outputs

The stable interface includes established user-visible command behavior and results.

Internal return values, object layouts, function return types, and module interfaces are not considered stable outputs.

The "`TAYKU-STATUS-CODE`" may be used as an internal command result mechanism, but its internal implementation must not be exposed as a guaranteed inner API unless explicitly defined as part of the user-facing interface.

· · ·
## 3.3 Dependencies

The stable interface must not depend on:

* A specific implementation language.
* A specific internal module layout.
* A specific internal function.
* A specific internal structure.
* A specific internal variable.
* A specific internal object layout.
* A specific internal ABI.
* A specific internal API.

The command interface may depend on externally defined Tayku formats and contracts where those formats are explicitly specified as stable interfaces.

· · ·
## 3.4 Source Contract

The command layer must provide a stable user-facing contract.

A conceptual interface may be represented as:

```js
/**
 * Executes a Tayku Web user-facing command.
 *
 * The command semantics form part of the stable interface.
 * The internal implementation is not part of the stable ABI/API.
 *
 * @param {string[]} argv User-provided command arguments.
 *
 * @returns {number} TAYKU_STATUS_CODE
 */
function execute(argv) {
	/* implementation-defined */
}
```

This source contract describes the responsibility of the command layer.

It does not require the actual implementation to preserve the function name, language, module, or source structure.

· · ·
## 3.5 Command Contract

An established command must preserve its documented user-facing semantics.

For example:

```sh
npx tayku-web verify --project foo
```

must continue to represent project verification even if the implementation behind "`verify`" changes completely.

The following implementation changes are permitted:

```text
JavaScript -> C
JavaScript -> Go
Module A -> Module B
Function X -> Function Y
Internal ABI v1 -> Internal ABI v2
```

provided that the established user-facing command behavior remains compatible.

· · ·
## 3.6 Command Behavior

The user-facing behavior of an established command must remain stable.

Changes that preserve the existing behavior may include:

* Performance improvements.
* Internal refactoring.
* Internal module replacement.
* Implementation language changes.
* Memory management changes.
* Data structure changes.
* Internal API changes.
* Internal ABI changes.
* Security improvements.
* Bug fixes that restore the documented behavior.

Changes that redefine what an established command means must not be introduced as ordinary implementation changes.

If a fundamentally different behavior is required, a new command or a new explicitly defined interface must be considered instead.

# 4. Error Handling

The stable interface includes errors that are explicitly defined as part of the user-facing command behavior.

Internal errors may change between implementations as long as the established user-facing behavior remains compatible.

* **Invalid Arguments**
	* "`INVALID ARGUMENT`": The user provided arguments that do not conform to the established command interface.
	* **Solution**: Use the documented syntax of the command.
* **Unsupported Interface Change**
	* "`INTERFACE CHANGE`": An implementation attempted to change an established user-facing command behavior in an incompatible way.
	* **Solution**: Preserve the established command behavior or introduce a new interface.
* **Internal Error**
	* "`INTERNAL ERROR`": An internal implementation failure occurred.
	* **Solution**: The implementation may handle or report the failure according to its internal architecture without exposing its internal ABI/API as a stable contract.
* **Permission Denied**
	* "`PERMISSION DENIED`": The operation could not be performed because of insufficient permissions.
	* **Solution**: Check the permissions required by the command and its implementation.
* **IO Error**
	* "`IO ERROR`": An input/output operation failed.
	* **Solution**: Check the relevant filesystem, registry, or other external resource.

# 5. Data Flow

## 5.1 User Command

The user invokes a Tayku Web command.

```text
User
 |
 v
Command Interface
 |
 v
Internal Implementation
 |
 v
Result
 |
 v
User
```

The user interacts with the stable command interface.

The internal implementation may change without changing the established command semantics.

· · ·
## 5.2 Node.js Implementation

The current implementation may use "`npx`":

```text
User
 |
 v
npx tayku-web
 |
 v
Node.js
 |
 v
Cli.js
 |
 v
Internal Modules
```

The "`npx`" invocation is an implementation-specific entry mechanism.

It is not a requirement that every future implementation use "`npx`".

· · ·
## 5.3 Future Implementation

A future implementation may be written in another language:

```text
User
 |
 v
tayku-web
 |
 v
C / Go / Other Implementation
 |
 v
Internal Modules
```

The internal architecture may be completely different while the user-facing command semantics remain compatible.

· · ·
## 5.4 Architecture Documentation Flow

When an internal component changes, the implementation change is reflected in its architecture documentation.

```text
Internal Change
 |
 v
Previous Implementation
 |
 v
New Implementation
 |
 v
Architecture Documentation
 |
 v
Historical Record
```

The documentation records both the previous and current implementations.

Historical implementation descriptions remain available so developers can understand how the component evolved across versions.

· · ·
## 5.5 Mainline Update Flow

Developer changes are integrated into the mainline repository and released according to the periodic update cycle.

```text
Developer Patch
 |
 v
Mainline Repository
 |
 v
Integration
 |
 v
Scheduled Mainline Update
 |
 v
New Version
 |
 v
User
```

A developer patch does not imply an immediate user release.

The normal integration point is the next scheduled mainline update.

· · ·
## 5.6 User Upgrade Flow

The Tayku Web Client may detect or communicate that a newer version exists.

```text
Installed Version
 |
 v
New Version Available
 |
 v
User Notification
 |
 v
User Decision
 |
 +----> Continue Current Version
 |
 +----> Upgrade
```

The client informs the user but does not force the user to upgrade.

The user is responsible for selecting and performing an upgrade.

# 6. Security

The stable interface must not require exposing internal implementation details to users or external programs.

The absence of a stable inner ABI/API allows security-sensitive implementation details to be changed when necessary.

Internal cryptographic, filesystem, registry, package, and verification implementations may therefore be replaced without requiring the user-facing command interface to change.

External software must not depend on undocumented internal interfaces for security-sensitive operations.

The user-facing interface must remain the primary supported integration point unless another interface is explicitly documented as stable.

Architecture documentation must describe security-relevant internal changes when those changes affect the implementation.

Historical documentation must not be interpreted as a guarantee that an old security implementation remains supported.

Users who continue to use an older version are responsible for their choice of version and its associated security characteristics.
